# 提取判定标准：什么值得长期保留

目标不是"把会话摘要写全"，而是**只捞出会改变未来行为的少数几条**。宁可少捞，不要凑数。

---

## 一、三问法（决定落点）

对每条候选依次问：

1. **换用户结论会变吗？** 会变 → 不是 user 层。
2. **换项目还成立吗？** 不成立 → 不是跨项目层。
3. **只是本次会话的临时状态吗？** 是 → 直接丢弃。

落点映射（先定语义层，物理文件由 `runtime-adapters.md` C 节按当前 runtime 解析）：

| 成立范围 | 语义层 | 跨工具默认落点 | 说明 |
|---------|--------|--------------|------|
| 只在本项目成立 | **项目层** | `<workspace>/AGENTS.md` | 写进仓库，跟着 git 走，20+ 工具原生读 |
| 换项目成立，换用户也成立 | **用户层** | 记忆工具 user 层 / 用户级指令文件 | 换个人用同一 agent 也该生效 |
| 换项目成立，但只对"我"成立 | **agent 层** | 记忆工具 main 层；无则只留在存档 | 跟工具链、运行环境、工作方式有关 |
| 仅本次会话 | 丢弃 | — | — |

> 注意区分第 2、3 行。agent 层存的是"任何用户的这个 agent 都适用的经验"，用户层存的是"这个人的偏好"。搞错层的记忆会在别的项目里污染判断。
>
> 某个 runtime 没有对应层级时（多数没有 agent 层），**不要硬造文件**——留在存档的「确认结果」里并告知用户，见 persistence-playbook 第五节。

## 二、证据强度排序

只从有证据的地方提取，按可信度从高到低：

| 级别 | 来源 | 例子 | 能不能进候选 |
|------|------|------|------------|
| A | **用户纠正 / 拒绝 / 打断** | "不对，我不是这个意思"、"别再问我要不要装"、"不要发布，保持本地" | ✅ 最高价值，几乎必进 |
| B | **用户明确说的偏好 / 约束** | "文件不要写进 workspace"、"确认要一条条来" | ✅ 进 |
| C | **用户在选项里做了选择** | 问卷里选了"只放仓库"而不是"仓库+安装" | ✅ 进（这是决策不是偏好） |
| D | 用户顺口提的需求 | "顺便把 README 也更新一下" | ⚠️ 只有形成"以后都这样"才进 |
| E | **助手自己的推断 / 总结** | 助手说"我认为这是个好习惯" | ❌ 不进。推断必须标 `[推断]` 并降级，默认不提取 |

**A 级证据的原文要抄进条目的"证据"字段。** 用户纠正过的东西，下次再犯就是失职。

---

## 三、硬性排除清单

以下内容**一律不进候选**，不管它看起来多重要：

1. 一次性参数：端口号、路径、ID、时间戳、本次任务的具体数值
2. 临时任务状态："还剩 3 个文件没改"、"等用户回复中"
3. 仓库里已经写着的事实：依赖版本、目录结构、API 签名、`git log` 能查到的任何东西
4. 官方文档能查到的事实：工具用法、API 参数、配置项含义
5. 助手自己的推测、还没验证的假设、plan 里的"打算做"
6. 敏感信息：任何 key / token / 密码 / 私钥 / 内部地址 / 他人个人信息
7. 已有记忆 / 指令文件里存在的同义条目（先把已有内容**完整读出来**比对，不要只靠 `search`——它可能静默返回空，详见 persistence-playbook）
8. 会话流水：做了什么、调用了哪些工具、跑了哪些命令（这些属于存档文档的时间线，不属于长期记忆）

## 四、条目格式

```
[D3] 结论前置的一句话（动词开头，≤ 60 字）
     证据：<用户原话片段> 或 <用户纠正："…">
     建议落点：项目层 / 用户层 / agent 层 / 丢弃
     理由：<为什么值得长期保留，一句话>
```

编号 `D1…Dn` 在本次运行内保持稳定，用户在问卷或纯文本回复里说的"D3 跳过"要能对应回原文。**给用户的表格里落点要写成具体的**（"AGENTS.md「目录约定」"、"长期记忆 user 层"），语义层只是内部判断用的。

**数量控制：3–8 条。** 超过 8 条说明在凑数——回头按排除清单再过一遍。少于 3 条很正常，说明这轮确实没什么值得长期留的，如实告诉用户"这次会话没有值得长期保留的决策"也是合格结果。

---

## 五、改写规则

条目写的是**结论**，不是过程。

| 规则 | 反例 | 正例 |
|------|------|------|
| 结论前置 | "我们讨论了一下发布方式，最后用户说" | "交付物默认不公开发布，只落本地" |
| 动词开头、含适用范围 | "关于安装位置的事" | "新建技能默认只写仓库，不自动安装到用户级目录" |
| ≤ 60 字 | 长段落 | 一句话 |
| 写行为，不写心情 | "用户这次有点烦" | "同类任务不要再反复问同一个确认问题" |
| 保留否定约束 | "要小心点发布" | "不要调用 website_deploy，除非用户明确要求上线" |
| 不写"这次" | "本次会话决定用 Node" | "跑脚本优先用 node，不要用 PowerShell 管道改文件" |

## 六、正反例对照

**✅ 好的条目**

```
[D1] 交付物默认不公开发布，只落本地
     证据：<用户纠正："A: Keep it local — don't publish">
     建议落点：用户层
     理由：用户明确纠正过一次；下次自动发布就是严重事故
```

```
[D4] 长任务派给子 agent 时，prompt 里必须要求"读完一批立刻写盘"
     证据：<用户纠正："派长任务给子 agent：必须要求增量落盘">
     建议落点：agent 层
     理由：中断时零产出是重复踩过的坑，与用户无关
```

```
[D6] 本仓库的技能统一放 skills/<name>/，含 SKILL.md + INSTALL.md
     证据：<用户在选项里选了"只放仓库">
     建议落点：项目层 —— AGENTS.md「目录约定」
     理由：只对本仓库成立，且是用户主动确认过的约定
```

**❌ 不该提取的**

| 内容 | 为什么排除 |
|------|-----------|
| "用了 init_skill.py 初始化" | 会话流水 + 官方文档可查 |
| "AGENTS.md 原本不存在" | 仓库当前状态，`ls` 就能查 |
| "用户可能喜欢更详细的文档" | 助手推断，无证据 |
| "session id 是 mvs_794e..." | 一次性 ID |
| "今天 20:35 开的会" | 临时状态 |
