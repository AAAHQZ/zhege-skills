# 条目模板

> 两版，按正文布局选一版。**不要混用。**
> 尖括号是占位符，落盘前全部替换掉；本文件里的小节顺序不要改。

---

## 版本 A · per-entry（一文件一条目）

存成 `<分类>/<id>.md`。**文件名必须 == `id`**，否则 `kb_lint.py` 的 `id-filename` 会报。

```markdown
---
id: <kebab-case-全局唯一>          # 建议带前缀，见下方前缀表
title: <一句话判断，不要写成词组>
category: <裸值，不带 NN- 序号>      # 目录叫 01-xxx 时这里写 xxx
problem: <用户会怎么问——保留用户原话形态，这是检索权重最高的键>
problem_variants:                   # 选填：其他常见问法
  - <问法 2>
  - <问法 3>
signals:                            # 用户处于某种错误认知状态的迹象
  - <信号 1>
  - <信号 2>
also_in: [<其他分类>]                # 选填：副分类，检索时要一起扫
sources:                            # 带类型的引用，不要写裸字符串
  - type: <book|paper|law|web|classic>
    ref: <作者《书名》年份 / 期刊 DOI / 书名+卷号篇名+原句 / URL>
    note: <选填：适用条件或争议>
---

## 解决的问题

<一两句。用户处于什么处境。这节是给人读的，不是给索引读的。>

## 核心判断

<一句话把判断说出来。敢下判断，不要写成"要具体情况具体分析"。>

## 机制

<讲透因果链：材料/案例 → 机制内核 → 为什么必然这样。
 **不要一上来就给结论**，先把材料讲清楚，再讲它推翻了什么常识。
 术语定框架，人话讲道理——读者不需要知道那些术语本身，
 他需要知道"他怕的不是你能力差，是你能力强又不可控"这种大白话。>

## 诊断信号

<怎么确认这条适用于当前这个人。要能回答"是/否"，不要"可能"。>

## 实操方法

<3–5 步，每步能回答"明天上班做什么"。>

1. <动词开头的动作>
2. <…>

## 备选计策

<2–4 条。**必须能分别独立于主线使用**；如果某条其实是主线同一动作的
 不同强度档位，就在这里标明它是档位，不要伪装成独立方案。>

### 计策 A · <名称>

- **博弈结构**：<这条为什么有效，一句话>
- **什么时候用**：<条件>
- **什么时候别用**：<条件>
- **动作骨架**：<步骤>
- **代价**：<写清>
- **场景实例**：<2–3 个具体的>

## 决策规则

<可判定的判据，不要"视情况而定"。
 优先用「缺失的那条信息，会不会让方案反向？」这种二值问句。>

## 反模式

<1–3 条常见的错做法，以及为什么错。>

## 边界

<**第一条永远是机制的失效条件**，不是套话。
 引用外部材料或古代案例时，第一条是「时代差异降级」：
 先点出当时的真实代价 → 明确降级规则 → 指出哪条机制不变。>

## 代价与风险提示

<用这套方法会付出什么、什么时候不该用。>

## 来源

<逐条列出，读者拿这里的信息能自己找到原句。
 外部材料与古文原文只放这节，正文用白话。>
```

### id 前缀表

前缀的作用是**让归属一眼可见**，并在下游撞名时**从结构上排除冲突**。

| 前缀类型 | 用于 |
|---|---|
| 书籍类前缀 | 从书籍蒸馏的条目 |
| 领域类前缀 | 面向特定人群的条目（技术人、管理者等） |
| 典籍类前缀 | 经典与史书类条目 |
| **个人前缀** | **你自己添加的条目** |

> **个人前缀的必要性**：条目和上游可能共用同一个 `references/` 命名空间。
> 上游还在更新，将来可能新增一条和你同名的 id——那时校验会报重复、
> 索引会出现两行，而且极难排查。个人前缀从**结构上**排除了撞车，
> 一眼也能认出哪些是自己加的。

## 版本 B · per-chapter（一文件多条目）

存成 `<NN>-<章名>.md`。**条号在章内唯一且不重复占用。**

**新条目追加在章末，不要插在中间**——条号是对外接口（纠错表单让人填「第 X 节第 Y 条」），
中间插入会让所有已有引用错位。

```markdown
# 第 N 章 <章名>

<章节导语，说清这一章回答什么问题。>

### <条号>. <标题>

<!-- 成本标签: 钱=<0|少|多> 时间=<少|中|多> 毅力=<否|些|是> 收益=<大|中|小> 口径=<口径1|口径2> -->
- 成本：<花掉什么，钱/时间/毅力>
- 说人话：<给没受过专业训练的成年人读的一句话>
- 收益：<换回什么，带具体数字>
- 证据等级：<A|B|C>
- 来源：<可定位的引用：DOI / 法条原文 / 官方网页>
- 备注：<争议、例外、适用人群、过程成本>

<正文：说清怎么做、什么情况下不适用。>

### <条号>. <标题>
...
```

### 标签行的要求

- 标签行是**给机器读的**（排序算账要用），所以**枚举值必须封闭**——
  封闭枚举才能机械排序
- 不要用自由文本。写「收益=高」而不是「还不错」，写「证据等级=B」而不是「有争议」
- 缺标签的条目 `kb_lint.py` 的 `label` 会报
- 章节文件通常**不需要** frontmatter，元数据在文件名和条目标题里

---

## 两版共用的硬要求

1. **出处必须能被读者自己核对。** 判据：读者拿你给的信息，能自己找到那句话。
   **只引一手来源**（期刊论文、法条原文、官方网页），不引二手转述。
2. **正文只做删减和替换，不做插入。** 批量改稿的脚本插入任何字符都可能造成
   看似正常的损坏（曾有规则给外文名补连接号，把普通词切成两段，损坏数百处，
   而校验查不出来）。**插入一律人工。**
3. **别把 `note: |` 写成 `note:|`** —— 空格丢了会让 YAML 解析失败。
4. **设一个厚度下限**（数千字符量级）。写不满两千字的方法论，
   通常是没想清楚，而不是内容简单。
