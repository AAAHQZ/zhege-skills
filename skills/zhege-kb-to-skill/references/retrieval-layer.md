# 检索层：让 agent 不必读完整个库

> 检索层的唯一任务：**在正确的时机，把最少的文字送进上下文。**
> 判据是「读完这些字之后，agent 有没有足够信息做一个不后悔的决定」。

---

## 一、三级渐进

| 级 | 读到哪 | 目的 | 体量参考 |
|---|---|---|---|
| 1 | 目录名 / 一张表 | 确定**去哪一类** | 几十行 |
| 2 | 分类索引 | 确定**哪一条** | 单类几 KB 到几十 KB |
| 3 | 条目全文 | 拿到**机制和边界** | 单条几 KB 到几十 KB |

**正常路径**：按分类读 → **只读命中的那一类索引** → 取命中最强的 1–2 条 →
读条目全文 → 按输出骨架输出。

长文件不要整篇读。最小的章节文件就有几十 KB，大的能到上百 KB——
**按关键词捞出相关条目，再把条目整条读完**。

### 第 1 级的索引要写成「问题表」而不是「标题表」

索引行的信息量决定了 agent 能不能定位准。

**差的索引**（只有标题）：

```
- 深度工作
- 反馈
- 权责对等
```

agent 只能靠标题猜，猜错就得回读，检索层白做。

**好的索引**（带用户的问法）：

```
| `deep-work` | 把不受打断的时间当稀缺资源管 | 我一天被打断十几次，深度时间从来没有过 |
| `self-feedback` | 要反馈就别问"你觉得怎么样" | 说了要改进，半年了一点没变 |
```

**结论：索引里必须有「用户会怎么问」这一列。只有标题的索引等于没有索引。**

## 二、三条硬规矩

### 规矩 1 · 判据要能现场取，不要凭记忆写

排序权重、阈值档位、计算公式这类东西**不要抄进消费侧**。
抄进去的那一刻就注定会漂移——原始文件改了，skill 里的副本不会跟着变。

正确做法是让 agent **当时从被引用的文件里取出来照着算**：

```
用 agent 自带的文件检索工具（grep / read）查 '权重定义行'，不要记一个数。
```

> 别写成 `grep -n '权重定义行' index.html` 这种固定命令——`grep` 在 Windows 上
> 不一定有（用户得先装 Git），而**任何 agent 都有内置的文件检索工具**，
> 那是唯一三平台都在的东西。

消费侧写清「这个档位怎么算、以哪个文件为准」，并给出一条能把它抠出来的命令。

**同时必须写降级路径**：拿不到那个文件时怎么办。典型写法是——
别报档位，改成把原始标签原样列出来让用户自己掂量。
**宁可少给一个结论，也不要给一个凭印象算出来的结论。**

### 规矩 2 · 索引会截断，难分时必须回去读全文

索引行是截断的（问题描述往往只留几十字）。所以**必须写死「难分时的下一步动作」**：

> 当某条只差一点、或两条难分时，去读那 1–2 个候选条目的元数据，
> 看完整的问题描述和其他问法变体，再定主推。**别只凭截断的索引就下结论。**

不写这一步，检索层在真正难的地方就失效了——而难的地方正是最需要它的地方。

### 规矩 3 · 权威顺序要写死

三层信息可能不一致：**索引行 / 条目元数据 / 物理目录**。必须明确谁说了算。

**以索引为准。** 理由很实在：**索引是检索层真正读到的东西**。
以索引为准，才能保证「检索到的」和「读到的」是同一条。

在消费侧写成一句显式的优先序，例如：

> 索引与正文不一致时，以索引为准（索引是检索层）。
> 三者权威顺序：**索引行 ＞ 条目元数据的分类字段 ＞ 物理目录**。

## 三、检索匹配：双通道

**不要只比 signals。**

`signals` 描述的是「用户处于某种**错误认知状态**」。而用户**已经持有正确直觉**，
或者正处于某个条目的**健康对照**情形时，signals 一条都不中——
但「用户会怎么问」那一列会**逐字命中**。

只用 signals 匹配，等于只认「想不清楚的人」，把「已经想清楚只差落地的人」全部漏掉。

**四个索引字段与权重**：

| 字段 | 用途 | 权重 |
|---|---|---|
| **用户会怎么问**（条目元数据里的问题描述） | 与用户问法**逐字或近逐字**重合 | **最高** |
| **判断**（标题） | 同一个问题 | 高 |
| `signals` | 处境符合 | 中 |
| `also_in` | 副分类条目也要一起扫 | — |

**命中判定**：

- 问题描述或标题命中 1 条即可
- 只靠 `signals` 的话要 **≥ 2 条**

**同档 tie-break**（两条都命中同一档时按顺序判）：

1. 用户自述的词与条目**逐字重合** → 那条优先。用户已经用了条目的原词，这是最硬的信号
2. 条目描述的**动作**和用户正在做的动作更接近 → 优先
3. 仍分不出 → 取**更基础的那条**做主推，另一条作副

**副分类不要降级**：某个条目虽然不在主分类目录下，但它的「用户会怎么问」
与用户原话逐字重合时，它就是主推。**因为它不在主分类目录里就把它降级，是丢强命中。**

## 四、兜底：全量索引什么时候读

全量索引很贵（十万行量级的索引能到几十 KB 到上百 KB）。
**只在两种情况读**：

- **拿不准属于哪一类** → 但先读 2–3 份相关的分类索引探路（比读全量省得多），
  还不行才读全量
- **清点式**（用户明确要看全部条目）→ 读全量，但**输出要收着**（默认只给分类摘要，
  不给全表）

推论两条，都要写进消费侧：

1. **兜底路径前面必须先有便宜的探路。** 不写的话 agent 会直接读全量。
2. **清点式要有输出上限。** 不写的话用户问「你有什么」，agent 会把整个索引吐出来。

## 五、索引腐化与同步

### 索引必须能被机器验证

「索引与正文是否同步」这道检查**必须存在于 CI 里**。理由不是偷懒，是现实：
**靠人记得跑的维护动作，在开放贡献的仓库里等于不存在**——本地链路要记得跑才会跑，
外部贡献者提交的内容更是完全跑不到。

### 只查不改

校验器**只报告，不写盘**。重建动作留给人本地跑。

理由是具体的：让 CI 往主分支推提交**会和本地分叉**；而且 CI 环境常常缺本地才有的
依赖（字体、图形栈、平台专用工具），生成物容易对不上。

### 索引要能被单独重建

入库闸门里必须包含「重建索引」这一步，通过判据是
**索引里的条目集合 == 目录下的文件集合**。对不上就是有文件没进索引。

对应到校验器：

```bash
# 判「有没有文件漏进索引」
"$PY" scripts/kb_lint.py --repo . --only index-sync

# 生成规范索引到 stdout
"$PY" scripts/kb_lint.py --repo . --emit-index
```

`--emit-index` **不写盘**。用文件写入工具把 stdout 内容落到一个临时文件，
再和 `skills/x/references/00-index.md` 逐行比对（用文件读取工具，
不要用 `diff`——它在 Windows 上不是内置命令）。

> 不要写成 `> /tmp/index.new.md` + `diff`：重定向行为各 shell 不同，
> `/tmp` 在 Windows 上解析成当前盘符根下的 `D:\tmp\`（通常不存在），
> `diff` 也不一定装了。三条里每一条都会在某个平台上静默失败。

**这道检查必须真的跑过一次**。没有实际拦截记录的话，它和没有这道检查没有区别。
建议在首次搭建时故意删掉一条索引行、跑一次校验、确认它报出来，再恢复。
