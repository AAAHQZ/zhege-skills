# 变更台账与贡献入口

> 目的：让**任何一句结论都能回溯到「哪次核实、依据什么、为什么这么改」**。
> 手段只有一个：**append-only**——一个变更批次一篇，永不重写历史。

---

## 一、为什么必须 append-only

原地改的问题不是「改起来麻烦」，而是**历史丢了**：

- 半年后有人质疑一条结论，**没人记得当初为什么这么写**
- 一次「纠错」顺手改掉了正确的地方，**无法发现也无法回滚**
- 同一个错误被反复提交，因为**没人查过之前有没有人提过**

台账目录本身就是这个库最值钱的部分——它让「这份资料为什么可信」变成**可审计的**。

规模上，一本几十万字的资料配上百篇台账是正常的量级，不必刻意精简。

---

## 二、台账格式

```markdown
# 追加：第 7 节第 22 条，被欠工钱先分清雇你的是谁（issue #60）

<日期>。issue #60 指出第 7 节第 2 条整条以劳动关系为前提，雇人的是自然人时
这两条路走不了，应当去法院。**追加在节末，没有插在中间，免得后面的条号整体顺延。**

## 没有照收的部分

- 读者草稿把「在小作坊做事」和「给朋友个人帮忙」归成一类，结论都是「走法院」。
  小作坊这一半与原文不符：劳动合同法第九十三条要求该单位或者其出资人支付劳动报酬……
  **按草稿写，会把本来能走免费路子的人支去打官司。**
- 草稿标题是「给个人干活前先看对方有没有营业执照」。有没有执照不是分界线，
  分界线是对方是不是在经营。条目标题和成本栏据此改写成三问：……

## 收进来的部分

- 自然人不是用人单位（劳动合同法第二条）。
- 读者建议的「备注里加一句边界说明和交叉引用」照做了……

## 1. 劳动合同法
- URL：<https://...>
- 原文：第二条「……」。第九十三条「……」。第九十四条「……」。

## 2. 司法解释
- URL：<https://...>
- 原文：第二十九条「……」
```

### 这份格式里有五个必填件

| 件 | 为什么必须有 |
|---|---|
| **标题带定位 + 来源**（`第 7 节第 22 条…（issue #60）`） | 能被搜到、能被引用 |
| **日期 + 为什么这么放** | 见下面「位置纪律」 |
| **`## 没有照收的部分`** | **最重要的一节**。记录驳回理由，让后来者知道这条路走过、为什么不通 |
| **`## 收进来的部分`** | 记录采纳了什么，让人能核对是否漏收 |
| **来源原文 + URL** | 读者能自己核到原句 |

**「没有照收的部分」不能省。** 它是台账里信息密度最高的一节——驳回理由往往比采纳内容
更能防止后人重犯。而且它逼着处理人**真的去读读者草稿**，而不是照单全收。

### 位置纪律：新条目追加在末尾

> **追加在节末，没有插在中间，免得后面的条号整体顺延。**

这一条极其重要。**条号是对外接口**——纠错表单里让人填的就是「第 X 节第 Y 条」。
中间插入会让所有已有引用错位，等于破坏整个库的对外契约。

如果确实需要重排，那是一次**单独的、显式的迁移**，要在台账里单独立篇说明，
不能混在一次普通纠错里。

## 三、贡献入口：先做成表单，写死「不要什么」

**纠错表单**

| 字段 | 必填 | 说明 |
|---|---|---|
| 哪一条 | ✅ | 「写节号和条号，比如『第 32 节第 2 条』」 |
| 哪里不对 | ✅ | 「**把原文那句抄过来**，再说应该是什么」 |
| 依据 | ✅ | 「期刊论文（DOI 或链接）、法条原文、政府或官方机构网页。**二手转述用不了。**」 |

**新内容表单**

| 字段 | 必填 | 说明 |
|---|---|---|
| 主题 | ✅ | 例：职称怎么评 |
| 想让库回答什么问题 | ✅ | 「写具体一点，比如『该去哪个机构、要准备什么材料』」 |
| 你知道的来源 | 选填 | 论文、法规、官方文件的链接 |

顶部还要有一条硬边界，写清**这个库只收什么样的内容**，以及**不收什么**
（例：只收能回答「花掉什么、换回什么」的建议；翻译请在自己的 fork 维护，不合进本仓库）。

### 三个可直接抄的做法

1. **「把原文那句抄过来」** —— 让人抄原文，而不是让人描述。
   抄的过程中他会自己发现到底哪里不对。
2. **明确列出拒绝哪类来源** —— 不写「请提供依据」，写「**二手转述用不了**」。
   前者会收到几百条转述，后者会收到几条能用的。
3. **「想让库回答什么问题」** —— 用**问题**而不是**主题**做输入门槛。
   主题是「健康」，问题是「体检套餐里哪些项目其实不用做」——后者才写得出来。

## 四、外部贡献进不了本地脚本，所以 CI 必须留一份

**凡是决定内容正确性的检查，都要有 CI 里的只读版本。**

理由很实际：本地那条链路**要记得跑才会跑**，而外部贡献者提交的内容**完全跑不到**。
一道只在本地存在的检查，在开放贡献的仓库里等于不存在。

配套的取舍：**只查不改**。让 CI 往主分支推提交会和本地分叉，
而且 CI 环境常常缺本地才有的依赖（字体、图形栈、平台专用工具），生成物容易对不上。
所以重建动作留给人本地跑，CI 只报告并返回非零退出码。

## 五、台账与校验器的分工

| 靠什么保证 | 工具 |
|---|---|
| 结构没坏（id 唯一、字段齐、小节齐、索引同步） | 校验脚本，进 CI，退出码非 0 |
| 内容对不对（结论是否有依据、依据是否支持结论） | **台账 + 人工判**，脚本查不了 |

**不要试图用脚本校验「内容对不对」。** 正确的分工是：把依据连同**原文引用**一起存进
台账或条目的来源字段，让人和未来的 agent 能自己复核；脚本只保证
**「依据存在且可定位」**，不保证「依据支持结论」。

后者是台账里 `## 没有照收的部分` 和人工复核的职责。
