# 正文布局：按条目切还是按章节切

> 决定「一个 .md 里装多少东西」。这个选择会一路影响元数据格式、检索粒度、校验脚本和
> 台账写法，所以要在动手转换之前定死。

---

## 一、判据

**两个条目能不能分别独立使用？**

- 能 → **per-entry**，一文件一条目
- 不能，必须连着上下文才读得懂 → **per-chapter**，一文件多条目

**有体系的大书要拆成多条，不是一条。** 拆到拆不动为止——判据是：
两条方法论能不能分别独立使用？能，就拆。

反面情形是把一整本书压成一条。那样得到的条目既没法独立使用，也没法被检索到具体方法，
用户问「我这种情况该怎么办」时只能拿到一整章的概述。

---

## 二、per-entry（一文件一条目）

```
references/
├── 00-index.md                 # 全量索引，只在兜底时读
├── _index/                     # 分类索引，只读命中的那一类
│   ├── 01-方法与效率.md
│   └── ...共 N 个
├── 01-方法与效率/             # 分类目录，目录名带序号前缀
│   ├── deep-work.md           # 条目文件
│   └── ...共 M 个
├── 02-向上相处/
└── ...共 N 类
```

**元数据放 frontmatter**（YAML）：

```yaml
---
id: deep-work                # 全局唯一，且 == 文件名
title: 深度工作：把不受打断的时间当稀缺资源管
category: 方法与效率           # 裸值，不带序号前缀（目录是 01-方法与效率）
problem: 我总是被打断，一整段深度时间从来没有过
signals:
  - 你一天被会议切碎超过 6 次
  - 你觉得"我在忙"但说不出交付了什么
sources:
  - type: book
    ref: 作者《书名》年份
also_in: [01-方法与效率]
---
```

**要点**：

- `id` 用**小写 kebab-case**，建议带前缀。`category` 写**裸值**，目录名带 `NN-` 序号。
- `problem` 写**用户会怎么问**（保留用户原话形态），这是检索时权重最高的匹配键。
  `signals` 描述的是「用户处于某种**错误认知状态**」——用户已持有正确直觉时
  signals 一条都不中，但 `problem` 会命中。
- `sources` 用**带类型的引用**（`type` + `ref`），不要写成裸字符串。类型可以是
  book / paper / law / web / classic，取决于这个库收什么。

**正文结构**：固定小节、顺序不能乱。一套够用的结构：

```
## 解决的问题 / ## 核心判断 / ## 机制 / ## 诊断信号 / ## 实操方法
## 备选计策 / ## 决策规则 / ## 反模式 / ## 边界 / ## 代价与风险提示 / ## 来源
```

**为什么强制固定小节**：`## 机制` 强制写原理、`## 边界` 强制写失效条件、
`## 代价与风险提示` 强制写方案的代价。**缺小节比写错内容更危险**——它逼着每个条目
回答「什么时候不成立」和「代价是什么」，而这两件事正是知识库和鸡汤的分界线。

## 三、per-chapter（一文件多条目）

```
book/
├── 01-不要早死.md            # 文件名自带节号和节名
├── 02-不要慢慢死.md
└── ...共 N 个章节
```

**元数据放条目标题 + 一行机器标签**：

```markdown
### 5. 把家里的食盐换成低钠盐（钾盐）
<!-- 成本标签: 钱=少 时间=少 毅力=否 收益=中 口径=死亡率 -->
- 成本：每袋贵几元
- 说人话：……死亡的概率低约 12%……
- 收益：脑卒中降 14%，心血管事件降 13%，总死亡率降 12%
- 证据等级：A
- 来源：作者, 期刊, 年份, DOI
- 备注：争议。肾功能不全、正在吃某些药的人不要用。……
```

**要点**：

- 条目标题格式 `### <条号>. <标题>`，条号在**章内唯一且不重复占用**。
  条号是对外接口——纠错表单里让人填的就是「第 X 节第 Y 条」，所以它必须稳定。
- 标签行用 HTML 注释，是**给机器读的**（排序算账要用），但它不给人眼造成干扰。
- 标签里的**枚举值必须封闭**（例：成本三项各 2–3 档、收益 3 档、口径若干个）。
  **封闭枚举才能机械排序**；写「还不错」这种自由文本，排序环节就没法自动化。
- 章节文件**通常没有 frontmatter**，元数据在文件名里。校验器在 per-chapter 布局下
  **不要求** frontmatter，只要求「写了就必须能解析」。
- 条目里**必须带来源和证据等级**。没有证据等级这一列，排序就少一个维度。

## 四、两种布局的对照

| | per-entry | per-chapter |
|---|---|---|
| 检索粒度 | 分类目录 → 分类索引 → 条目全文 | 目录名 → 章节文件 → 关键词捞条目 |
| 索引形态 | 分类索引 ×N + 全量索引 | 一张「本章回答什么问题」的表 |
| 元数据 | YAML frontmatter | 标题行号 + HTML 标签行 |
| 适合 | 素材天然离散、条目能独立使用 | 素材有体系、条目要连着读 |
| 条目校验 | 字段 + 小节 + id 唯一 | 标签行 + 条号唯一 |
| 校验器 | `kb_lint.py`（默认 per-entry） | `kb_lint.py` + `"layout": "per-chapter"` |

---

## 五、通用要点（两种布局都适用）

### 出处必须能被读者自己核对

判据只有一条：**读者拿你给的信息，能自己找到那句话。**

- 书籍类：写清 **作者 + 书名 + 年份**
- 经典与史书：写清 **书名 + 卷号/篇名 + 原句**，**原文只放进元数据区，正文用白话**
- 学术与法规：写清 **可定位的链接或条款号**
- **只引一手来源**（期刊论文、法条原文、官方网页），**不引二手转述**——
  博客、公众号、内容农场这类转述一律不收

### 条目厚度有下限

设一个正文字符数下限（数千字符量级），低于下限直接判不合格。理由是——
**一条写不满两千字的方法论，通常是没想清楚，而不是内容简单。**

对应到校验器：`"min_body_chars": 4000`。

### 一份东西只存一处

索引清单、章节表、条目目录这类东西**只存一份**，别的地方要查就现场去查。
**两份目录必然会漂移**，而漂移的目录比没有目录更糟——它会让检索层看起来是好的。

要判据的时候**现场去取**（grep 出来），不要在消费侧抄一份。

### 目录名带序号 = 给排序留位置

`01-` 到 `09-` 意味着**将来可以插一个新类**而不必重命名所有文件，
也不会打乱既有的目录顺序。新增分类是常事，别为了「先不排序」而不编号。

### 条目 id 要带归属前缀

前缀的作用是**让归属一眼可见**，并在下游撞名时**从结构上排除冲突**。
建议按素材类型分配前缀，并给自己手动添加的条目用一个独立前缀——
条目和上游可能共用同一个 `references/` 命名空间，将来上游新增一条同名 id 时，
会出现重复报错、索引出现两行，而且极难排查。独立前缀从结构上排除了撞车。
