# 并行蒸馏：按主题簇切，不按素材条数切

> 这是整份方法里**唯一一条没有替代方案**的纪律。按条数切分产出的一定是重复，
> 而且重复得很「合理」——每个 agent 都在认真干活。

---

## 一、事故形状

第一次全量蒸馏时，在同一分类下起了多个 agent，每个拿一份素材切片各自蒸馏。
结果产生了**大量跨批次重复**——某个分类一度有 51 条，其中**约 14 条是重复的**
（"比较/嫉妒" 4 条、"我不行" 3 条、"低谷期向内" 3 条……），
因为它们读的是同一批素材、写的是同一个主题。

最终写出 206 条，手工合并回 178 条。

注意 14/51 和 206/178 这两个数字：接近三成的重复率、二十多条合并工作量——
这些全是纯损耗，而且是在**已经花了全部算力之后**才发现的。

---

## 二、根因：主题聚类是 agent 自发做的

关键在于理解**为什么会这样**：

```
按条数切：
  agent A 拿 14 条素材 → 自己聚类 → 聚出「嫉妒」
  agent B 拿 13 条素材 → 自己聚类 → 也聚出「嫉妒」
  agent C 拿 12 条素材 → 自己聚类 → 还是「嫉妒」
                                    ↑
                        没有人告诉它们这三簇是同一簇
```

**每个 agent 都在正确地做主题聚类。问题出在聚类这一步被复制了 N 遍。**

所以正确的切法是把聚类**提前、只做一次**：

```
先聚类（一次，全局）→ 再分派 → 一簇一 agent
  簇「嫉妒」      → agent A（独占）
  簇「我不行」    → agent B（独占）
  簇「低谷期向内」→ agent C（独占）
```

---

## 三、四条规则

### 1. 先聚类，后分派

由一个人（或一个 agent）**先把整个分类的素材按主题聚成 N 个簇**，
再把**簇**分派给 agent。一个簇只给一个 agent。

### 2. 一簇一 agent

如果某个分类只有 5–6 个簇，就**只起 5–6 个 agent**，
**不要为了并行度把一个簇拆给两个 agent**。

> 这条是反直觉的：并发数应该由**簇数**决定，不是由「素材有多少条」决定。
> 簇少就少起几个。宁可并发低，不要制造重复。

### 3. 跨分类的重叠要提前定边界

一个主题可能同时像两个分类（比如既是「方法」又像「人际」）
——**派活前先定它归哪个分类**，另一个分类的 agent 要**明确知道这条不用你管**。

> 派活说明里要**显式列出不属于你的主题**。不写这条，边界外的 agent 也会去写。

### 4. 收尾必须去重

跑机械检测 + **人工语义检测**，重复的做**合并**而不是删除。

---

## 四、去重的两步

### 机械筛：抓字符和标题的相似

字符 n-gram + 标题相似度。

### 人工判：抓「同一主题不同措辞」

**字符串相似度抓不到「同一主题不同措辞」。** 所以机械筛完**必须**再人工扫一遍。

实操做法是把某类的所有 `id + title` 列出来看：

```python
import yaml, glob
for f in sorted(glob.glob('references/<分类>/*.md')):
    fm = yaml.safe_load(open(f, encoding='utf-8').read().split('---', 2)[1])
    print(f"{fm['id']:28} {fm['title'][:60]}")
```

机械检测和结构报告分成两个脚本：一个只管找可疑重复对，一个顺带输出结构指标和异常条目。

### 合并的判断标准（三档，别一律合并）

| 关系 | 处理 | 理由 |
|---|---|---|
| 两条在回答**同一个用户问题** | **合并** | 索引里两行，用户会挑花眼 |
| 同一主题的**不同角度** | **保留**，各加 `note` 说明分工 | 检索时会命中不同的问法 |
| 只是**相关** | **保留，不动** | 本来就该分开 |

### 合并是折入，不是删除

> 同主题的重复做**合并**（把独有内容折进保留条），**不是删除**——
> **合并后计策数应该上升，不是下降。**

**这是一条可验证的验收标准**：如果合并之后你那一类的条目没变少，
或者变少的同时内容也少了，那就是合并做错了。
「合并后计策数应该上升」是最好用的自检信号。

---

## 五、派活模板里要写死的东西

派活说明必须包含：

1. **这一簇的主题是什么**（一句话）
2. **id 前缀** —— 且要提前查过**没被占用**。条目和上游可能共用同一个命名空间，
   撞名的后果是重复报错、索引出现两行、极难排查。派活前先 `ls` 目标目录确认
3. **不属于你的主题**（边界外的，明确说「不用你管」）
4. **结构要求**：必填字段、小节顺序
5. **校验命令**：入库前必须跑什么
6. **增量落盘**：读完一批立刻写盘，**不要攒到最后统一写**

第 6 条对**子 agent** 尤其重要。父会话一旦中断或超时，所有后台子 agent 会被连带取消；
如果它们的模式是「先把全部素材读完 → 再统一写文件」，取消时磁盘上一个字都没有，
**读素材的时间全部作废**。

---

## 六、并发上限

并发上限**取决于具体 runtime 的配置**，不是通用数字。
桌面端每个父会话通常有默认上限（常见为 4），派超出会直接失败而不是排队。

**做法**：先查自己所在 runtime 的实际并发上限，再决定起几个 agent。
**不要假设上限，也不要为了填满并发去拆簇。**
