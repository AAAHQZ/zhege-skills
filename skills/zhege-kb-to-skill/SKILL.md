# zhege-kb-to-skill — 把知识语料做成能长期维护的 skill

> 这套方法解决的是「转换之后」的问题。转一次谁都会，难的是半年之后：
> 加了新内容检索层没更新、引用了正文里没有的数字、有人提了纠错改完没人说得清当初为什么
> 那么写、正文被一个批量脚本改坏几百处。
> 所以本 skill 的产出不是「一份 skill」，而是**五件套**。

---

## 一、这个 skill 做什么

把「一堆资料」变成「一个 agent 能可靠引用、并且长期可维护的 skill」。

---

## 二、五件套

这五件事必须分开落位。混在一起写，短期省事，长期每一件都会拖垮另外四件。

| 件 | 落位 | 缺了会怎么死 | 落地形态 |
|---|---|---|---|
| **① 内容** | 独立数据目录，**绝不塞进 SKILL.md** | SKILL.md 涨到几万 token，每次调用全量进上下文；改一个字要重读整个库 | `<分类>/<id>.md`（按条目切）或 `<节号>-<节名>.md`（按章节切） |
| **② 检索层** | 索引 + 分级渐进 + **判据现场取** | 要么得读完整个库才敢答，要么凭印象瞎猜 | 分类索引 + 全量索引，或一张「本库回答什么问题」的表 |
| **③ 消费契约** | 另一个**薄** skill，只写路由 / 追问 / 输出骨架 / 边界 | 每次回答结构都不一样，没法验收、没法回归 | 独立的消费侧 SKILL.md |
| **④ 生产规则** | 再一个 skill 或项目指令文件，**不写进消费侧** | 改数据的规矩和消费侧混在一起，两边互相污染 | 生产侧 SKILL.md + `docs/` 下的规范 |
| **⑤ 闸门 + 台账** | **只读**校验脚本进 CI + append-only 变更记录 | 正文悄悄漂了没人知道；改动不可追溯、不可回滚 | 结构校验 + 行为契约测试 + 变更记录目录 |

### ① 内容必须独立，消费侧必须薄

消费侧与正文的体量比应当控制在**百分之一量级**。消费侧装的是
「怎么找、怎么排、怎么写、什么不做」，**一行正文都不装**。

判断标准：**消费侧里出现任何一段具体内容，就是漏到这来了。**

### ④ 生产规则和消费契约绝不同居

这是硬规矩，不是风格偏好。生产侧只管「怎么把新内容做进来」，消费侧只管
「怎么把已有内容用出去」。混在一个文件里，改数据的动作会顺手改掉回答口径，
反过来回答口径的变化也会污染入库标准，两边都变得不可信。

具体做法：生产侧写自己的 SKILL.md，或写进项目指令文件（`AGENTS.md`），
由它单向指向消费侧。反向也要指一条——让人改内容之前先知道消费侧在哪。

> ⚠️ 跨工具注意：项目指令文件优先用 `AGENTS.md`（AAIF/Linux Foundation 标准，20+ 工具原生读）。
> **Claude Code 不读它**，需要在 `CLAUDE.md` 里写一行 `@AGENTS.md` 引入。

### ⑤ 校验器只查不改

校验工具**永远不写盘**。重建、修复、格式化这类动作单独给一个显式开关，默认只报告。

理由是具体的：校验器跑在 CI 上，**让 CI 往主分支推提交会和本地分叉**，
而且 CI 环境常常缺本地才有的依赖（字体、图形栈、平台专用工具），生成物容易对不上。

## 三、第 0 步：先判在哪个阶段

别一上来就搬文件。先判断用户在哪一站：

| 用户说的是 | 阶段 | 做什么 |
|---|---|---|
| 「帮我把这堆资料做成一个 skill」 | **A 建库** | 走第三节完整七步 |
| 「这个 skill 怎么加新内容」 | **B 扩容** | 先跑第五节的现状体检，再只补缺的那件 |
| 「它答错了 / 漏了内容」 | **C 修内容** | 定位是检索层漏了还是正文缺了，**不要**趁机重构流水线 |
| 「怎么防止它以后变烂」 | **D 补防线** | 走第四节的 ⑤ 件 + `scripts/kb_lint.py` |
| 「想拿这套方法审一下我这个库」 | **E 体检** | 只跑第六节的自检清单，出报告，不改文件 |

**C 最容易做错**：用户说「答得不好」，九成是**条目不够**或**索引没同步**，
不是契约写错了。先跑一遍 `kb_lint.py` 再决定动不动 SKILL.md。

---

## 四、七步工作流

### 第 1 步 · 盘点现状（不写任何文件）

先产出一张盘点表，回答四个问题：

1. **正文现在在哪？** 多少文件、多大、总量多少
2. **有没有 id？** 有的话唯一吗、和文件名一致吗、谁生成
3. **检索层是什么形态？** 索引文件、表格、目录名，还是什么都没有
4. **有没有变更记录？** 有的话是 append-only 还是原地改

再问用户三个问题（**一次最多问 2 个，别做问卷**）：

- 这个库接下来还会不会继续加内容？会 → ⑤ 件是必需品；不会 → 可以先只做 ①②
- 结论要能被外部核对吗？要 → 必须有出处字段和变更台账
- 谁维护？一个人还是接受外部提 PR？后者 → 必须做第六节的贡献入口

### 第 2 步 · 定布局

正文按**条目**切还是按**章节**切：

| | per-entry（一文件一条目） | per-chapter（一文件多条目） |
|---|---|---|
| 适合 | 素材天然离散，每个条目互相独立 | 素材有体系、有脉络，条目要连着读才成立 |
| 元数据放哪 | frontmatter（`id` / `title` / `category` / `sources`） | 条目标题 + 一行机器可读标签 |
| 检索粒度 | 分类目录 → 分类索引 → 条目 | 目录名 → 章节文件 → 关键词捞条目 |

**判据**：两个条目**能分别独立使用** → 按条目切；必须连着上下文才读得懂 → 按章节切。

**有体系的大书要拆成多条，不是一条。** 拆到拆不动为止：两条方法论能不能分别独立使用？
能，就拆。

细则见 `references/corpus-layouts.md`。

### 第 3 步 · 建检索层

三级渐进，让 agent 不必读完整个库：**先定位 → 再缩小 → 最后才读全文**。

三条硬规矩：

- **判据要能现场取，不要凭记忆写。** 排序权重、阈值、计算公式这类东西，
  要让 agent 当时从被引用的文件里 grep 出来照着算。抄进 skill 就会漂移。
- **索引会截断，难分时必须回去读全文。** 在消费侧写死「难分时的下一步动作」，
  否则 agent 会硬选一条——而难的地方正是最需要它的地方。
- **权威顺序要写死。** 索引行、正文元数据、物理目录三者可能不一致，必须明确谁说了算。
  判据是：**以索引为准，因为索引才是检索层真正读到的东西。**

细则见 `references/retrieval-layer.md`。

### 第 4 步 · 写消费契约

这是「agent 拿到资料之后怎么答」。**只写四件事，一件都不要少**：

1. **路由判据**——从用户的话路由到哪一类。**必须写判据之间的优先序**，
   并且**给每条优先序写明「为什么排在那个位置」**。没有理由的排序，执行时会自己发挥。
2. **追问纪律**——什么信息缺了必须问、问几个、问几轮，以及**信息够不够的可操作判据**。
3. **输出骨架**——小节名固定，**照用不改写**。
4. **边界**——什么不接、什么不做、什么必须声明「库里没有」。

其中最值钱、最容易被漏掉的是**「库里没查到怎么办」**。必须要求如实声明而不是硬凑。

细则见 `references/answer-contract.md`。

### 第 5 步 · 写生产规则

**独立文件**，不要混进消费侧。至少要有：

- **收什么不收什么**：把排除项写明（营销钩子、明确的违法行为、以无辜第三方为对象的伤害）
- **入库流水线**：从原始素材到成品的分阶段，每阶段有**闸门**，通过条件写死
- **排重规则**：机械筛 + 人工语义判；**重复要合并不是删除**
- **并行纪律**：见第七节

### 第 6 步 · 配闸门

把不变量翻译成**机器能跑的断言**，接进 CI。逐条翻译方法见
`references/invariants-and-ci.md`，通用校验器已经写好：`scripts/kb_lint.py`。

```
"$PY" scripts/kb_lint.py --repo <库根>                  # 全量校验，只查不改
"$PY" scripts/kb_lint.py --repo <库根> --only id-unique,index-sync
"$PY" scripts/kb_lint.py --repo <库根> --emit-index     # 打印规范索引，人工比对
```

> `$PY` 是探测出来的解释器名：Unix 通常 `python3`，Windows 通常 `python` 或 `py`。
> `--emit-index` 打到 stdout 不写盘，用文件写入工具捕获后落盘——
> **不要用 shell 重定向**，那在三个平台上行为各不相同。

**格式能被 lint 守住，行为契约只能靠另一种方式守**：写测试断言**承载关键判据的那句
具体句子还在**。路由判据、追问纪律这类东西在文档里读起来完全正常，
删掉一句「看起来啰嗦」的话没有任何 lint 会报错，但坑就重新挖开了。

### 第 7 步 · 开贡献入口 + 定变更台账

外部提 PR / 报纠错之前，先把入口做成表单，并**明确写出拒绝哪类来源**。
只写「请提供依据」会收到大量二手转述；写「只引期刊论文、法条原文、政府或官方机构网页」
才能收到能用的。

变更台账用 **append-only**：一个变更批次一篇，永不重写历史。细则和现成格式见
`references/change-ledger.md`。

## 五、不变量

这四条任何时候不能改。改任何一条都要**同步四处**，否则文档和实际行为会悄悄分叉：

1. **路由规则**（有哪几类、什么情况路由到哪类）——改它要同时改：schema 规范、生产侧规则、
   消费侧 SKILL.md、**行为契约测试**。漏一个就分叉。
2. **元数据格式**能被机器解析（按条目切是 YAML frontmatter；按章节切是标签行格式）
3. **id 全局唯一**（按条目切额外要求：文件名 == id）
4. **答案要能指回正文**——这是整个库可信度的地基

## 六、交付前自检

- [ ] 正文在独立目录，`SKILL.md` 里**没有**具体内容（只有找法、算法、结构、边界）
- [ ] 检索层三级可用，且**判据能现场 grep 出来**
- [ ] 消费契约四件事齐全：路由判据（**带优先序和理由**）/ 追问纪律 / 输出骨架 / 边界
- [ ] 「没查到怎么办」有明确写法，要求如实声明、不许硬凑
- [ ] 生产规则独立成文件，没混进消费侧
- [ ] 不变量已翻译成断言，`kb_lint.py` 跑通
- [ ] 索引与正文同步，且**有一个只读的检查在守它**
- [ ] **做过一次「故意造错」验证**：造几类典型错误，跑校验，逐项确认它真的报
- [ ] 变更走 append-only 台账，能从任一结论回溯到依据

倒数第二条别跳过。**没验证过会报错的闸门等于没有闸门。**

---

## 七、并行：大批量转换的唯一正确切法

要并行派多个 agent 蒸馏素材时，**按主题簇切，不按素材条数切**。

根因要理解清楚：**主题聚类是每个 agent 都会自发去做的一步。**
按条数切分时，agent A 拿到前 14 条自己聚出「嫉妒」，agent B 拿到后 13 条也聚出「嫉妒」——
没人告诉它们这两簇是同一簇，于是每个都认真写了一遍「怎么处理嫉妒」。
这不是 agent 不认真，是结构性的。

所以正确的切法是把聚类**提前、只做一次**。细则（先聚类后分派、一簇一 agent、
跨分类边界、收尾去重）见 `references/parallelism.md`。

---

## 边界

- 本 skill 产出**方法与骨架**，不产出内容本身。具体条目要靠素材蒸馏，
  那部分在第五节指向的生产侧规则里。
- 不做事实核查。出处是否可靠、结论是否成立，要按 `references/change-ledger.md`
  的台账格式逐条核，那是另一件工作。
- 不改已有 skill 的内容。看到「答错了」先分清是条目问题还是契约问题，
  别把修 bug 变成重建流水线。
